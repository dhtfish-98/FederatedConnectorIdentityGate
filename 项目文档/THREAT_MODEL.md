# Threat model and limits

The failure mode is an application mapping two signed federated identities to one local account because their email strings match. The local test baseline intentionally makes that mapping; it is not attributed to Dex or another third party. The guard accepts only a token verified with the configured Dex issuer, the configured application audience, a flow-specific nonce and a valid signature and expiry. It requires a verified email and signed federated connector/user identifiers, then binds its own account key to the issuer and both identifiers. Resource reads require the active application session to own the stored resource.

The live test covers two self-written OIDC sources, two Dex connectors, same email with different upstream user IDs, and the same upstream user ID through different connectors. It checks both cross-resource directions, persistence after reopen, and revocation of the prior browser session during a connector switch. Wrong nonce, audience, trusted issuer, signature, expired token, absent federated claims and unverified email are rejected. The wrong-issuer test changes the configured discovery URL and observes denial; it does not exercise a second live Dex issuer. The expiry test uses the same real Dex-signed token before and after its signed expiry.

The state file is a single-process experiment. The caller must protect its containing directory from other users and supply a trusted path. The package does not protect an attacker-controlled parent directory, detect symlink races across the full path, lock across processes, perform a directory fsync after rename, encrypt local data at rest, or handle large production account stores. The caller must pin the trusted issuer/client, hold authorization state and nonce per browser flow, consume them once, and implement code exchange and any applicable PKCE policy. `VerifyDexIDToken` checks the caller-supplied nonce in the signed token; it does not store or enforce nonce single-use. An active bearer session can be used by someone who steals it; the tested rotation only revokes the prior session when a new login presents it. The local OIDC sources, Dex and application exchanges run over loopback HTTP and do not establish deployment TLS, production key custody, federation trust policy, or external authorization.

The test demonstrates a local defensive control, not a Dex vulnerability, provider safeguard impact, CVP qualification, or CVP approval. Those remain **OPEN**.
